# Спецификация: безопасная наблюдаемость Sentry на staging

## Цель

Дать администратору Terraforming Mars staging воспроизводимые сведения о неожиданных серверных сбоях — тип ошибки, стек, версия приложения и окружение — без передачи игровых, пользовательских и сетевых данных. Изменение не должно затрагивать production и не должно менять ответы API или ход игры.

## Пользовательские сценарии

### Сценарий 1 — расследование неожиданного сбоя

**Как** администратор staging, **я хочу** увидеть неожиданную серверную ошибку со стеком, версией и отметкой окружения, **чтобы** связать её с конкретным кодом и воспроизвести причину.

**Проверка:** при искусственно вызванной неожиданной ошибке staging формируется одно диагностическое событие с требуемым техническим контекстом и без запрещённых данных.

### Сценарий 2 — ожидаемая ошибка клиента

**Как** администратор staging, **я хочу**, чтобы ожидаемые ошибки валидации и допустимого пользовательского ввода не попадали в Sentry, **чтобы** сигнал не смешивался с рабочими ошибками клиента.

**Проверка:** известная ожидаемая ошибка сохраняет прежний HTTP-ответ и не формирует диагностическое событие.

### Сценарий 3 — безопасное отключение

**Как** оператор сервера, **я хочу**, чтобы интеграция оставалась выключенной при неполной конфигурации или вне staging, **чтобы** случайно не включить отправку данных в другом окружении.

**Проверка:** отсутствие адреса приёма событий либо окружение, отличное от `staging`, полностью отключает отправку событий и не мешает запуску сервера.

## Функциональные требования

| ID | Требование |
|---|---|
| FR-001 | Система должна включать отправку диагностических событий только при одновременном наличии настроенного адреса приёма событий и точном значении окружения `staging`. |
| FR-002 | Система должна регистрировать неожиданные ошибки верхнего уровня серверной обработки запроса. |
| FR-003 | Система должна регистрировать неожиданные ошибки обработки игрового ввода, которые сейчас перехватываются и журналируются сервером. |
| FR-004 | Система не должна регистрировать ожидаемые ошибки приложения и пользовательского ввода. |
| FR-005 | Диагностическое событие должно содержать тип ошибки, очищенное от игровых и пользовательских идентификаторов сообщение, стек вызовов, версию приложения и окружение. |
| FR-006 | При включённой и выключенной интеграции существующие HTTP-статусы, тела ответов, журналирование и игровое поведение должны сохраняться. |
| FR-007 | Сбой или недоступность внешнего приёмника событий не должны прерывать серверную обработку запроса и не должны менять ответ клиенту. |

## Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-001 | В события, контекст и дополнительные диагностические данные нельзя включать тела запросов, заголовки, cookies, query-параметры, IP-адреса, breadcrumbs, идентификаторы игроков и игр. |
| NFR-002 | Должен применяться принцип минимизации: разрешён только технический контекст, явно перечисленный в FR-005. |
| NFR-003 | Интеграция не должна добавлять новый обязательный секрет или параметр для запуска сервера без Sentry. |
| NFR-004 | Автоматические тесты должны проверять как разрешённые поля, так и отсутствие каждого класса запрещённых данных. |
| NFR-005 | Изменение должно быть отражено в актуальной карте кода, включая точки вызова, затрагиваемые компоненты и покрывающие тесты. |

## Ограничения

| ID | Ограничение |
|---|---|
| C-001 | Настройка секретов на сервере, push, PR, merge, staging-deploy и любые production-изменения не входят в этот пакет. |
| C-002 | Клиентский мониторинг, трассировка производительности, профилирование, сессии и запись пользовательского взаимодействия не входят в объём. |
| C-003 | Публичные API-контракты и схема сохранённой игры не меняются. |

## Пограничные случаи

- Адрес приёма событий задан, но окружение отсутствует, имеет другой регистр или иное значение: отправка выключена.
- Окружение равно `staging`, но адрес приёма событий отсутствует или пуст: отправка выключена.
- Ошибка не является экземпляром стандартного `Error`: сервер продолжает прежнюю обработку, а диагностический слой не раскрывает исходный объект целиком.
- Одна ошибка проходит через несколько уровней обработки: она не должна превращаться в несколько одинаковых событий в рамках одного пути.
- Внешний приёмник медленный или недоступен: ответ клиенту не ждёт успешной доставки события.

## Допущения

- Версия приложения доступна из существующих метаданных сборки или пакета и не требует нового пользовательского идентификатора.
- Значение `staging` является единственным разрешающим значением окружения в рамках этой задачи.
- Серверные логи остаются действующим локальным каналом диагностики; Sentry дополняет, но не заменяет их.

## Критерии успеха

- Автоматическая проверка подтверждает, что интеграция выключена во всех конфигурациях, кроме сочетания адреса приёма событий и окружения `staging`.
- Для каждого выбранного пути неожиданной ошибки создаётся ровно одно событие с типом, очищенным сообщением, стеком, версией и окружением.
- Ожидаемые ошибки приложения и ввода создают ноль событий.
- Проверки с заполненными телом, заголовками, cookies, query, IP и игровыми идентификаторами подтверждают отсутствие этих данных в итоговом событии.
- Все существующие и новые профильные тесты, статический анализ и сборка проходят без изменения наблюдаемого поведения API.

## Вне объёма

- Подключение DSN и иных секретов на staging-сервере.
- Выпуск релиза, настройка Sentry project/release pipeline и загрузка sourcemaps.
- Мониторинг браузерного клиента, производительности или бизнес-метрик.
- Исправление найденных через Sentry продуктовых ошибок.
