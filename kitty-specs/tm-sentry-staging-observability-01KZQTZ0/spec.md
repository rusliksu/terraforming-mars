# Спецификация: расширенная наблюдаемость Sentry на staging

## Цель

Дать администратору Terraforming Mars staging достаточный контекст для воспроизведения неожиданных серверных сбоев: сообщение ошибки, полный стек вызовов, место обработки запроса, версию приложения, идентификаторы игры и игрока и игровой input. Сетевые и auth-источники не прикладываются структурно, а известные секретные и сетевые форматы удаляются из разрешённых строк; production, HTTP-ответы и ход игры не затрагиваются.

## Пользовательские сценарии

### Сценарий 1 — воспроизведение неожиданного сбоя

**Как** администратор staging, **я хочу** увидеть сообщение ошибки, полный стек, route/method, версию, game/player IDs и связанный gameplay input, **чтобы** сопоставить событие с кодом и условиями возникновения без ручного сбора локальных логов.

**Проверка:** искусственная неожиданная ошибка формирует ровно одно событие, содержащее весь доступный разрешённый контекст выбранной границы.

### Сценарий 2 — секрет внутри диагностического контекста

**Как** оператор сервера, **я хочу**, чтобы известные форматы токенов, cookies, паролей, session-данных, DSN, URL query и IP удалялись даже из сообщения ошибки, стека или вложенного gameplay input, **чтобы** расширенная диагностика не превращалась в канал утечки учётных данных.

**Проверка:** уникальные secret sentinel-значения, помещённые во все разрешённые источники, отсутствуют в итоговом Sentry envelope и заменены маркером фильтрации.

### Сценарий 3 — ожидаемая ошибка клиента

**Как** администратор staging, **я хочу**, чтобы ожидаемые ошибки приложения, валидации и malformed JSON не попадали в Sentry, **чтобы** диагностический поток содержал только неожиданные сбои.

**Проверка:** известная ожидаемая ошибка сохраняет прежний HTTP-ответ и не формирует событие.

### Сценарий 4 — безопасное отключение

**Как** оператор сервера, **я хочу**, чтобы интеграция оставалась выключенной при неполной конфигурации или вне staging, **чтобы** случайно не отправить данные из другого окружения.

**Проверка:** отсутствие DSN, валидной версии сборки либо точного окружения `staging` полностью отключает отправку и не мешает запуску сервера.

## Функциональные требования

| ID | Требование | Статус |
|---|---|---|
| FR-001 | Система должна включать отправку диагностических событий только при одновременном наличии настроенного адреса приёма событий, точном значении окружения `staging` и валидной версии сборки. | Согласовано |
| FR-002 | Система должна регистрировать неожиданные ошибки верхнего уровня серверной обработки запроса. | Согласовано |
| FR-003 | Система должна регистрировать исходные неожиданные ошибки обработки игрового ввода, включая ошибки, которые затем преобразуются в ожидаемый `InputError`. | Согласовано |
| FR-004 | Система не должна регистрировать ожидаемые `AppError`, `InputError` и malformed JSON; их прежние ответы должны сохраняться. | Согласовано |
| FR-005 | Событие должно включать исходный тип и сообщение ошибки после удаления секретов, полный стек вызовов без локальных переменных, release и environment. | Согласовано |
| FR-006 | Когда данные доступны выбранной границе ошибки, событие должно включать HTTP method, route path без query, raw game ID, raw player ID и разобранный gameplay input после удаления секретов. | Согласовано |
| FR-007 | Каждое событие должно содержать фиксированную категорию границы захвата, позволяющую отличить process, request и конкретные PlayerInput paths. | Согласовано |
| FR-008 | При включённой и выключенной интеграции существующие HTTP-статусы, тела ответов, журналирование и игровое поведение должны сохраняться. | Согласовано |
| FR-009 | Сбой или недоступность внешнего приёмника событий не должны прерывать серверную обработку запроса и не должны менять ответ клиенту. | Согласовано |

## Нефункциональные требования

| ID | Требование | Статус |
|---|---|---|
| NFR-001 | Система не должна структурно прикладывать request/response headers, cookies, query string, IP, user-agent, session/auth объекты или иные поля вне явного allowlist. | Согласовано |
| NFR-002 | Ко всем разрешённым строкам и объектам, включая сообщение, стек и gameplay input, должны рекурсивно применяться denylist ключей и распознаватели перечисленных форматов: header/cookie lines, URL query/fragment, IPv4/IPv6, Bearer/JWT, DSN, credential assignments и PEM private key. Произвольный неизвестный секрет без распознаваемого ключа или формата не считается гарантированно обнаружимым. | Согласовано |
| NFR-003 | После фильтрации gameplay input должен детерминированно сериализоваться в JSON и измеряться как UTF-8 через `Buffer.byteLength`; итоговое `request.data` не должно превышать 65 536 байт. При превышении отправляется валидный JSON-объект с `truncated: true`, исходным размером и UTF-8-безопасным preview, также укладывающийся в лимит. | Согласовано |
| NFR-004 | Автоматические тесты должны одновременно доказывать присутствие каждого разрешённого поля и отсутствие каждого класса запрещённых данных в финальном SDK envelope. | Согласовано |
| NFR-005 | Интеграция не должна добавлять новый обязательный секрет или параметр для запуска сервера без Sentry. | Согласовано |
| NFR-006 | Изменение должно быть отражено в актуальной карте кода, включая точки вызова, затрагиваемые компоненты и покрывающие тесты. | Согласовано |

## Ограничения

| ID | Ограничение | Статус |
|---|---|---|
| C-001 | Настройка секретов на сервере, push, PR, merge, staging-deploy и любые production-изменения не входят в этот пакет. | Согласовано |
| C-002 | Клиентский мониторинг, автоматический сбор HTTP-контекста, tracing, profiling, sessions, breadcrumbs и запись пользовательского взаимодействия не входят в объём. | Согласовано |
| C-003 | Публичные API-контракты, схема сохранённой игры и БД не меняются. | Согласовано |
| C-004 | Полное состояние игры, имя игрока и произвольные свойства throwable не прикладываются: разрешены только явно перечисленные диагностические поля. | Согласовано |

## Пограничные случаи

- Message или stack содержит header/cookie line, URL с query/fragment, IPv4/IPv6, Bearer/JWT, DSN, password/token assignment либо private-key block: распознанный фрагмент заменяется, остальная диагностическая строка сохраняется.
- Gameplay input содержит секретный ключ на любой вложенности: значение заменяется рекурсивно; исходная структура остальных игровых данных сохраняется в пределах лимита.
- Gameplay input после фильтрации и UTF-8 JSON-сериализации превышает 65 536 байт или имеет циклическую структуру: событие остаётся отправляемым с валидным детерминированным усечённым представлением.
- Ошибка возникает при получении игрока до чтения input: событие содержит доступные route/method/game/player IDs, но не выдумывает gameplay input.
- Неожиданная undo-ошибка преобразуется в `InputError`: исходная ошибка с доступным input регистрируется один раз до преобразования.
- `JSON.parse` отклоняет malformed body: ошибка не регистрируется, а прежние status и response message сохраняются.
- Ошибка проходит через несколько уровней: она не превращается в несколько одинаковых событий в рамках одного пути.
- Внешний приёмник недоступен: ответ клиенту не ждёт успешной доставки.

## Допущения

- Руслан явно разрешил передачу raw game/player IDs и gameplay input для staging-диагностики при сохранении запрета секретов.
- Route означает только нормализованный path без query string.
- Гарантия приватности состоит из структурного allowlist и распознавания перечисленных ключей/форматов; произвольную свободную строку, не имеющую распознаваемой сигнатуры, нельзя надёжно классифицировать как секрет.
- Версия приложения берётся из существующих build metadata; `n/a` не является валидной версией.
- Серверные логи остаются локальным дополнительным каналом диагностики.

## Критерии успеха

- Для каждого выбранного неожиданного пути создаётся ровно одно событие с доступными message, full stack, boundary, method/path, release/environment, game/player IDs и gameplay input.
- Автоматическая проверка подтверждает ноль событий для ожидаемых ошибок и всех конфигураций, кроме DSN + `staging` + валидный build head.
- Финальный envelope содержит разрешённые sentinel-значения игрового контекста; запрещённые источники отсутствуют, а перечисленные secret/header/cookie/query/IP sentinel-форматы, в том числе внедрённые непосредственно в thrown message и stack, отфильтрованы.
- Итоговое `request.data` не превышает 65 536 UTF-8-байт и при усечении остаётся валидным JSON-объектом с детерминированным маркером, не меняя HTTP-ответ и не прерывая обработку ошибки.
- Все профильные тесты, статический анализ и сборка проходят без изменения наблюдаемого поведения API.

## Вне объёма

- Подключение DSN и иных секретов на staging-сервере.
- Выпуск релиза, настройка Sentry project/release pipeline и загрузка sourcemaps.
- Мониторинг браузерного клиента, производительности или бизнес-метрик.
- Исправление найденных через Sentry продуктовых ошибок.
