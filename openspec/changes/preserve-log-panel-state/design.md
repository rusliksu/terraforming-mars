## Контекст

`App.update()` увеличивает `playerkey` после получения нового view model. Vue поэтому размонтирует и заново создаёт `PlayerHome`, включая `LogPanel`. Существующий код сохраняет прокрутку только во время обновления уже смонтированного экземпляра и не переживает этот lifecycle.

## Цели / Вне целей

**Цели:**

- Сохранить режим, фильтр, auto-follow и прокрутку между двумя экземплярами `LogPanel` одного участника.
- Дать пользователю явный короткий путь обратно к свежим логам.
- Сохранить существующие правила загрузки и видимости сообщений.

**Вне целей:**

- Удаление или изменение глобального `playerkey`.
- Постоянное хранение настройки после закрытия вкладки.
- Изменение API, server-side фильтрации или hidden-information boundary.

## Решения

Состояние хранится в module-level `Map`, ключом служит `ParticipantId`. Перед размонтированием компонент записывает только UI-state; новый экземпляр читает его при mount и загружает тот же набор логов с восстановлением позиции. Это минимальнее и безопаснее, чем менять принудительный rerender всего `PlayerHome`, добавлять parent plumbing или использовать `localStorage`.

`Latest logs` сбрасывает режим в `Last 100`, фильтр в `All`, включает auto-follow и запускает существующий `getRecentLogs(true)`.

## Риски / Компромиссы

- [Состояние хранится до перезагрузки вкладки] → это соответствует проблеме обычных игровых refresh и не создаёт новый persistence-контракт.
- [Module-level `Map` может хранить несколько participant IDs] → объём ограничен числом открытых в одной вкладке игровых страниц и содержит только несколько примитивов.
- [Изменение `playerkey` могло бы убрать remount] → не применяется из-за широкого влияния на весь `PlayerHome`.

## План применения

Внести client-only diff, проверить remount behavior и действие `Latest logs`, затем выполнить focused tests, lint и build. Откат состоит из удаления module-level state и новой кнопки; данные и API не мигрируются.
