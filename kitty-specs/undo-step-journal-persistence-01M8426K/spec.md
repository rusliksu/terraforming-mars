# Спецификация: сохранение журнала шагового отката в базе данных

## Цель

Экспериментальный шаговый откат (`undoStepOption`) должен переживать рестарт сервера. Журнал шагов переезжает из памяти процесса в базу: корень действия хранится ссылкой на уже существующее append-only сохранение, сами шаги — отдельными строками в транзакции сохранения партии. Поведение партий без `undoStepOption` не меняется.

## Контекст и проблема

`Game.actionReplayState` (`src/server/Game.ts:216`, тип `ActionReplayState` из `src/server/game/ActionReplay.ts`) содержит `rootSnapshot: SerializedGame`, `entries: ActionInputEntry[]` (лимит `MAX_ACTION_REPLAY_ENTRIES = 32`), `currentActorId`, `currentPromptFingerprint`, `resetBeforeNextInput` и `lastStepBackLogStartIndex`. Поле не входит в `SerializedGame`, поэтому после рестарта шаговый откат недоступен до конца партии (зафиксировано в `docs/variants/undo.md`).

Инфраструктура для персистенции уже есть: append-only сохранения, genesis-снапшот и упорядоченный журнал входов в v2 gateway (`src/server/actionGateway/ActionGateway.ts`, коммит `02122a15f`), `stateHashAfter` на каждый принятый input, `POST /player/undo/v2` без деструктивного восстановления.

## Пользовательские сценарии

### US-001 — Откат после рестарта сервера

Игрок делает два шага внутри действия (например, Hi-Tech Lab), сервер перезапускается. После возврата в партию кнопка шагового отката доступна, откат возвращает к предыдущему логическому шагу с теми же картами.

### US-002 — Безопасный отказ при расхождении

Если состояние партии ушло вперёд без журнала (другой клиент, выключенная опция, ручная правка), шаговый откат недоступен, но партия загружается и играется дальше без ошибок и без изменения состояния.

### US-003 — Изоляция существующих режимов

Партия с `undoOption: true` и `undoStepOption: false` продолжает работать через legacy-откат действия; таблицы журнала для неё не читаются и не пишутся.

### US-004 — Долгая сессия

При серии из более чем 32 шагов журнал хранит последние 32 шага, более старые вытесняются, откат на вытесненный шаг недоступен.

## Функциональные требования

| ID | Требование |
| --- | --- |
| FR-001 | Для партии с `undoStepOption: true` журнал пишется в БД в той же транзакции, что и `Database.saveGame`; отдельного фонового писателя нет. |
| FR-002 | Схема содержит `game_action_replay(gameId, seq, rootSaveId, actorId, promptFingerprint, inputJson, logStartIndex, continuesThroughNextInput, createdAt)` и `game_action_replay_head(gameId, rootSaveId, currentActorId, currentPromptFingerprint, resetBeforeNextInput, lastStepBackLogStartIndex, updatedAt)`. |
| FR-003 | `rootSnapshot` в БД не дублируется: хранится `rootSaveId` существующего сохранения, снапшот читается из append-only сохранений. |
| FR-004 | При загрузке партии `GameLoader` восстанавливает head и записи по возрастанию `seq`, проверяя наличие `rootSaveId` и совпадение `promptFingerprint`. |
| FR-005 | Лимит `MAX_ACTION_REPLAY_ENTRIES = 32` сохраняется; при переполнении в той же транзакции удаляются записи за пределами лимита. |
| FR-006 | `resetBeforeNextInput`, смена актора и начало нового корня действия полностью перезаписывают журнал, а не накапливают записи между действиями. |
| FR-007 | Fail-closed: отсутствие корня, отсутствие head, расхождение fingerprint или битый `inputJson` делают шаговый откат недоступным, не влияя на загрузку и ход партии. |
| FR-008 | Партии без `undoStepOption` не читают и не пишут таблицы журнала; legacy `GameLoader.undo()` не меняется. |
| FR-009 | Причины отказа журнала наблюдаемы: `replay_loaded`, `replay_saved`, `replay_dropped_missing_root`, `replay_dropped_fingerprint`, `replay_dropped_corrupt`. |
| FR-010 | Миграция аддитивная, без обратного заполнения: партии, начатые до миграции, шагового отката после рестарта не получают. |

## Нефункциональные требования

| ID | Требование |
| --- | --- |
| NFR-001 | Дополнительная задержка сохранения партии с включённым журналом не более 5 мс по p95 на локальной PostgreSQL-фикстуре. |
| NFR-002 | Объём журнала ограничен 32 записями на партию; на партиях без опции дополнительные записи не появляются. |
| NFR-003 | Запись и чтение журнала не меняют сериализацию `Game.serialize()` и контракт `stateHash`. |
| NFR-004 | Изменение покрывается regression-first тестами, включая интеграционные тесты на рестарт, и проходит server lint/build/test gates. |

## Тесты на рестарт

- T-1: два шага, эмуляция рестарта (сброс кэша `GameLoader`), восстановление журнала, успешный шаговый откат, совпадение `stateHash`.
- T-2: дрейф `promptFingerprint` между сохранением и загрузкой — `replay_dropped_fingerprint`, партия играбельна.
- T-3: удалённое корневое сохранение — `replay_dropped_missing_root`.
- T-4: 40 шагов — остаются последние 32, граница доступного отката корректна.
- T-5: исключение после вставки записей — транзакция откатывается, журнал не изменён.
- T-6: партия без `undoStepOption` — таблицы пусты.
- T-7: два рестарта подряд без новых шагов — журнал не теряется.
- T-8: клиентский тест `showStepBack` — доступность кнопки соответствует восстановленному состоянию.

## Вне скоупа

- Изменение значений по умолчанию `undoOption` и `undoStepOption`.
- Изменение legacy-пути `GameLoader.undo()` и `restoreGameAt`.
- Перенос журнала на клиент или в localStorage.
- Обратное заполнение журнала для уже идущих партий.
- Staging/prod deploy без отдельного разрешения.

## Критерии приёмки

- Тест T-1 сначала падает на текущем коде (журнал теряется после сброса кэша) и проходит после изменения.
- Поведение шагового отката после рестарта совпадает с поведением без рестарта, включая объединённые логические шаги.
- Fail-closed ветки не приводят к изменению состояния партии и логируют причину отказа.
- Партии без `undoStepOption` и партии с одним `undoOption` не меняют поведение.
- Релевантные server-тесты, lint/build и `git diff --check` зелёные.
- Изменение доставляется task-owned PR в `main`; staging и prod — отдельные delivery gates.
