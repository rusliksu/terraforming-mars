## Контекст

Live-источник рейтинга содержит три ключа одного человека: `александр` (6 игр), `саша` (2 игры) и `quattrowow` (2 игры). Игра `gfb80e36623be` уже завершена с корректным игроком `Quattrowow`, цветом `pink` и не требует изменения в `game.db`. Канонизация имён централизована в `elo/player_name_aliases.json`, а выбор профиля и визуальный цвет дополнительно задаются в TypeScript-профилях и статической Elo-странице. `tm-sync-elo.py` пересобирает Elo и расширенную статистику из сохранённых игр.

Операция затрагивает live/prod и потому следует staging-first release flow. Базовый рабочий каталог сервера грязный и устаревший. Первоначальный worktree от `origin/main` оказался небезопасным для точечной поставки: ветка не совпадает с текущей live-lineage и несёт другие alias/code изменения. Итоговая реализация должна вестись в новом отдельном worktree от точного live-коммита `d9853c3c49f30649a3a6ef8ab1c1cf26e59543ee`.

## Цели / Не цели

**Цели:**

- закрепить `Quattrowow` как единственное каноническое имя для трёх вариантов;
- закрепить розовый цвет профиля в форме создания игры и статистике;
- пересобрать производные данные без потери истории;
- проверить результат на staging и затем на prod с backup и откатом.

**Не цели:**

- не переписывать `game.db` и player id завершённых игр;
- не менять места, VP, корпорации или исходы матчей;
- не объединять других Александров/Саш без отдельного подтверждения;
- не включать посторонние незавершённые изменения из базового worktree.

## Решения

### 1. Канонизация через общий alias-файл

В `player_name_aliases.json` добавляются self-alias `quattrowow` и алиасы `александр`, `саша`, указывающие на `Quattrowow`. Это тот же источник, который используют server Elo sync и построение профилей.

Альтернатива — вручную отредактировать только `elo-data.json` — отклонена: следующая синхронизация снова разделит профили и изменение не будет долговечным.

### 2. Один seed-профиль Quattrowow

Seed `Александр/blue` в `PlayerProfiles.ts` заменяется на `Quattrowow/pink` с историческими алиасами. Статическая Elo-страница получает соответствующую розовую привязку, чтобы UI не зависел от позиции профиля в сортировке.

Альтернатива — полагаться на циклический цвет карточек — отклонена: цвет изменится при изменении рейтинговой сортировки.

### 3. Пересборка производных данных штатным sync

После поставки alias-файла используется `tm-sync-elo.py`, который повторно нормализует сохранённые результаты и хронологически пересчитывает рейтинги и `stats.json`. Исходная `game.db` остаётся read-only для этой операции.

Альтернатива — сложить текущие агрегаты трёх профилей — отклонена: Elo зависит от последовательности матчей, поэтому корректен только полный хронологический пересчёт.

Текущая репетиция в памяти на live-снимке SHA-256 `d8024e685b7e1d15ab3e57770d7f444abffb15718d2bb68237fbacc4b25cf93d` показала:

- replay обрабатывает все 359 игр, а спортивная проекция и порядок остаются неизменными;
- прямое переименование есть в 8 играх, рейтинговые поля меняются в 109 играх и 162 результатах; объединённое множество изменений — 113 игр;
- кроме объединяемого профиля меняются рейтинговые агрегаты 13 игроков; изменение placement Elo находится в диапазоне 0…+7;
- `Quattrowow` получает 10 игр, placement Elo 1484 и VP Elo 1500; количество профилей меняется с 40 до 38;
- повторный replay побитово идентичен первому.

Это зафиксированный диагностический снимок, а не вечная константа: непосредственно перед live-миграцией отчёт строится заново и привязывается к новому hash.

### 4. Staging-first и точный promote

Код проходит unit/regression tests, затем разворачивается в staging, проверяется через API, Elo UI и browser console. В prod продвигается ровно тот же артефакт. До prod-пересборки копируются `elo-data.json`, `data.json` и `stats.json` в отдельный timestamped backup-каталог с контрольными суммами.

### 5. Эксклюзивное окно live-миграции

Prod sync запускается таймером `tm-sync-elo.timer` каждые пять минут и уже использует `flock /tmp/tm-sync-elo.lock`. Перед promote таймер останавливается, текущий `tm-sync-elo.service` должен быть неактивен, а дальнейшие backup, финальный preflight и ручной sync выполняются под тем же lock. Таймер возвращается только после успешной проверки либо полного восстановления backup. `tm-elo.service` является API и отдельно не выполняет пересчёт.

### 6. Release lineage совпадает с prod

Task-ветка создаётся от SHA, указанного текущим `/home/openclaw/tm-runtime/prod/current/release.json`, а не от `origin/main`. Перед staging проверяется, что alias-diff относительно live содержит только `quattrowow`, `александр`, `саша`, а replay-impact возвращается к изолированному эффекту Quattrowow без `Nuke` и других несогласованных объединений.

## Риски / Компромиссы

- [Распространённые имена могут принадлежать разным людям] → область намеренно ограничена подтверждёнными Русланом профилями; новые неоднозначные случаи потребуют per-game override.
- [Полный пересчёт изменит рейтинги не только суммированием трёх строк] → это ожидаемое следствие правильной хронологии; до/после сохраняются агрегаты и число игр.
- [Фоновый sync может писать одновременно] → `tm-sync-elo.timer` останавливается, oneshot завершается, а backup и ручной replay выполняются под штатным `/tmp/tm-sync-elo.lock` без параллельного release/deploy lock.
- [Между репетицией и записью может завершиться новая игра] → финальный preflight привязан к SHA-256; при изменении hash impact-report пересчитывается, а запись не начинается по устаревшему отчёту.
- [Продвижение нового артефакта может включить чужие изменения] → release source и список commit проверяются перед staging; promote использует exact tested artifact.
- [База `origin/main` содержит не выпущенные alias-изменения] → task-commit переносится на точный live SHA; полный diff и impact-report сравниваются с live до сборки.
- [Сбой после записи части JSON] → backup включает все три производных файла; после восстановления проверяются hashes и публичные endpoint.

## План миграции

1. Создать отдельный worktree от точного live SHA и перенести только алиасы, seed-профиль, статический цвет и regression tests этого change.
2. Выполнить целевые тесты, сборку и strict OpenSpec validation.
3. Проверить чистоту release source и отсутствие параллельного deploy; развернуть commit в staging.
4. На staging запустить/дождаться sync и проверить: один `Quattrowow`, розовый UI, 10 игр, нет ключей `александр`/`саша`, console errors отсутствуют.
5. Остановить `tm-sync-elo.timer`, дождаться неактивного oneshot-service и занять `/tmp/tm-sync-elo.lock`.
6. Создать timestamped backup производных prod JSON с SHA-256 и построить финальный impact-report на этом же hash.
7. Продвинуть exact staging artifact в prod и выполнить одну ручную штатную пересборку, не освобождая sync-lock между проверяемыми этапами.
8. Проверить локальные и публичные JSON, API игры `gfb80e36623be`, Elo UI и логи sync/API; затем вернуть timer.
9. При нарушении инвариантов восстановить три JSON из backup до возврата timer; код откатывать штатным runtime rollback только при проблеме артефакта.
