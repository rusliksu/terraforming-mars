## Архитектура

1. Отдельный клиентский набор `src/client/wrybit/**`, собственные стили и ресурсы; исходная ревизия, лицензия и локальные адаптации перечислены в manifest. Обычная оболочка и исходные компоненты сохраняются.
2. Один выключенный по умолчанию режим в настройках: существующий experimental_layout заменяет ограниченную компоновку полным «Интерфейсом Wrybit». Значение false сохраняется; явное прежнее включение остаётся включением. Корневая оболочка выбирает представление; новые тяжёлые ресурсы загружаются по требованию. Обычные стили не смешиваются со стилями Wrybit.
3. Существующий App остаётся владельцем запросов, обновления модели, авторизации и отправки действий. UI Wrybit получает наши типизированные модели. Его компоненты не импортируют серверный код или AI.
4. Реестр форм покрывает все варианты нашего PlayerInputModel. Обработчики отправки и канонические расчёты принадлежат текущему серверу. Формы Wrybit меняют представление и взаимодействие, сохраняя InputResponse, ограничения и доступность.
5. Недостающие сведения для интерфейса проецируются из наших данных. Допустимы узкие read-only view-модели/маршруты с существующими проверками доступа; изменение игровых решений, эффектов, сериализации или AI запрещено.
6. Переключение оболочки сохраняет актуальный незавершённый ввод. Проверяется совпадение карты, оплаты и контекста запроса до/после; обновление серверного шага инвалидирует устаревший локальный выбор.
7. Большие исходники Wrybit разделяются по ответственности: создание игры; оформление типов карт; мобильные экраны, навигация и формы; статистика. Нельзя просто переименовать многотысячный файл и объявить его изолированным.

### Сохранение ввода между представлениями

Проверенный контекст запроса сохраняет настоящую карту и оплату при polling, но смена двух разных PlayerHome уничтожила бы вложенную форму. Постоянный владелец — один наш `WaitingFor → PlayerInputFactory` под App, вне сменяемых представлений. Classic и Wrybit регистрируют DOM-host; Teleport перемещает существующее поддерево без второго контроллера или сериализации частичных ответов. Во время смены host используется скрытый постоянный контейнер; позднее освобождение старого host проверяет идентичность регистрации.

Обновление из GET и успешной отправки применяет одну ревизию ввода. Новый контекст инвалидирует вложенные формы; callbacks прежней ревизии не применяют модель и не возобновляют polling. До готовности нового представления действует classic, а ошибка загрузки сохраняет его. Выбор клетки и quick-greenery дополнительно перепривязываются к новому DOM поля, сохраняя SpaceId, а не старый HTMLElement.

Это уточнение способа исполнения согласованного сохранения ввода: наши модели, цены, сетевые обработчики, протокол, правила и AI сохраняют владельцев. Границы, пользовательские требования, среды и delivery gates не изменяются. Проверки включают две разные ветки представления, nested or/projectCard, начальный выбор, поле, задержку/отказ загрузки и точный JSON нашего WaitingFor.

Сверка действующего контракта: 20 уникальных типов PlayerInputModel и 21 тип InputResponse; дополнительный `policy` не имеет отдельной входной модели. Полнота определяется актуальным типизированным реестром; отсутствующая форма policy не создаётся.

## Обнаруженные несовпадения

- Wrybit StatsPage запрашивает `/api/stats/games`; у нас такого маршрута нет. Наш `/api/stats` — административный, защищённый, не является заменой публичной статистики. Сначала проверить имеющиеся публичные ELO/завершённые данные, затем предоставить минимальную публичную проекцию завершённых игр без рук, драфта или сырого состояния. Не раскрывать административный endpoint.
- BaseInputModel Wrybit содержит sourceCard, а наш контракт содержит собственную annotation и дополнительные модели торговли. Представление адаптируется к нашему контракту; типы форка не подменяют наши.
- Инициализация, polling, собственные страницы, перенос состояния и серверные уведомления отличаются. Корневая логика Wrybit не становится вторым независимым клиентским контроллером.
- Дополнительные библиотеки форка не импортируются автоматически. Для снимков/иконок сначала используются существующие средства; новая зависимость обосновывается фактическим UI-потребителем.
- Ресурсы с совпадающими путями не перезаписываются поверх обычного интерфейса. Карточные данные берутся из нашего генератора.
- Наши custom/rebalanced/fanmade параметры и новые типы ввода обязаны сохраняться. Непроверенную комбинацию нельзя записать как готовую.

## Доставка

После согласования — реализация, тесты, проверяемый PR в custom repo, CI, merge и staging из точного origin/main. Перед staging снять baseline, после — проверить manifest, API, UI и сохранность prod. Подготовить proof PR в upstream fork для полного UI; если адаптации нельзя выразить чисто, показать готовый альтернативный proof-пакет для отдельного решения.

Новая production-выкладка требует отдельной команды на готовый пакет и свежей проверки realtime-партий. Отсутствие такого разрешения не мешает реализации, проверкам и staging. Копирование/восстановление рабочей БД запрещено на всех этапах.

## Уточнение приёмки, согласовано 15 октября 2026

Промежуточные WP принимают собственные компоненты и локальные сценарии по contracts/stage-coverage.md. Критерий не требует заранее выполнить работу зависимого последующего WP. Полные сквозные строки UI-01…UI-21 остаются открытыми с владельцем до реального полного сценария; в WP07 обязательна их полная сверка. Component proof не заменяет итоговый сценарий или staging. Требования, итоговые gates и последовательное штатное исполнение Spec Kitty сохраняются (approval.md).

Для сохраняемого ввода каждый наш stateful controller остаётся постоянным. Режим меняет только типизированное представление, загружаемое через WrybitShell; stateful descendants получают локальные hosts/порталы своего owner. PaymentForm сохраняет ключ cardName, Or/And сохраняют наши исходные индексы и callbacks. Один глобальный INPUT_HOSTS продолжает обслуживать только WaitingFor под App; вложенные формы не используют его. Это уточняет реализацию уже согласованного сохранения ввода, без нового доменного контроллера или foreign ledger/defaults.
