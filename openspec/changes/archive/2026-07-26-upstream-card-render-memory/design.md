## Контекст

`CardRenderer.builder` создаёт вложенные объекты `renderData` при конструировании карт и глобальных событий. Клиент получает эти данные из заранее собранного `cards.json`; работающий HTTP-сервер их не читает, но сейчас всё равно тратит CPU при инициализации и удерживает объекты в памяти. Официальный upstream решил это в PR `#8337` двумя последовательными коммитами `451759a888` и `06989b8205`.

Custom server содержит собственные изменения, поэтому весь `upstream/main` не переносится: в scope входит только поведение PR `#8337`. Primary checkout занят другой задачей, реализация ведётся в task-owned worktree от `origin/main`.

## Цели / Вне целей

**Цели:**

- Не выполнять callbacks `CardRenderer.builder` и не создавать отдельные деревья `renderData` в live runtime.
- Сохранить полное построение `renderData` в `export_card_rendering.ts`, тестах и других non-live процессах.
- Сохранить игровой код, клиентский `cards.json` и внешние контракты без изменений.
- Перенести upstream-решение узко и с проверяемой эквивалентностью.

**Вне целей:**

- Остальные 25 upstream-коммитов, включая HTTP metrics, IP quota, PostgreSQL, MarsBot, переводы и визуальные исправления.
- Измерение или обещание конкретного объёма экономии памяти: upstream PR не задаёт стабильный числовой контракт.
- Изменения API, gameplay, сохранений, БД, переменных окружения или клиентского UX.
- Prod deploy: он возможен только по отдельной явной команде Руслана.

## Решения

1. Перенести два upstream-коммита как единый узкий change, сохранив их порядок. Первый переносит module-scope builders в конструкторы; второй добавляет live-маркер и ранний возврат из `CardRenderer.builder`.
2. Хранить live-маркер как необратимое process-local состояние в `src/server/utils/server.ts`. Он выставляется только entrypoint-ом `src/server/server.ts`, поэтому build/export процессы остаются в обычном режиме без новой конфигурации.
3. Возвращать один общий пустой `ICardRenderRoot` и не вызывать переданный callback. Это устраняет и CPU-работу builder-а, и удержание отдельных деревьев.
4. Не добавлять reset-функцию в production API ради тестов. Live-ветку проверять в изолированном дочернем процессе, чтобы необратимый маркер не загрязнял остальные server tests; существующий `CardRenderer.spec.ts` продолжает проверять non-live ветку.
5. Проверить `npm run make:cards` и отсутствие изменения generated card metadata. Это защищает пользовательский вид карт лучше, чем проверка только типов.
6. После targeted checks выполнить server build и staging backend smoke с фиксацией точного SHA/release manifest. Staging не расширяет scope до prod.

## Риски / Компромиссы

- [Live-маркер выставлен слишком поздно, и часть module-scope builders уже выполнилась] → перенести ровно upstream-набор module-scope `renderData` в конструкторы и проверить отсутствие оставшихся таких объявлений в затронутых классах.
- [Build/export ошибочно получает пустые метаданные] → маркер выставляется только server entrypoint-ом; запустить `npm run make:cards` и проверить отсутствие generated diff.
- [Необратимый process-local флаг ломает другие тесты] → live-сценарий выполнять в отдельном процессе без test-only reset API.
- [Механический перенос 48 определений создаёт незаметный semantic diff] → сравнить touched scope с upstream-коммитами, отдельно проверить локальные изменения в пересекающихся файлах и выполнить server tests/build.
- [Staging drift или нездоровый сервис] → перед deploy переснять обязательный snapshot и остановиться по существующим deploy guards.

## План применения

1. Перенести upstream-коммиты `451759a888` и `06989b8205` в task-owned branch, разрешая только понятные scoped overlaps.
2. Добавить изолированную регрессионную проверку live-ветки и выполнить targeted tests, `make:cards`, server build и проверку diff.
3. Задеплоить точный проверенный SHA на staging штатным guarded path и выполнить backend health/release smoke.
4. После полной evidence архивировать change, включить код и архив OpenSpec в один task-owned PR.
5. Откат staging при регрессии — повторный deploy предыдущего зафиксированного staging artifact штатным release-процессом. Prod не изменяется.
